范围：首次登录候选 → 原会话读取 → 旧因子停用 → 新因子登记与激活 → 凭据提交/会话交接 → 中断、重启和显式身份验证续接。使用本机模拟服务、临时私有存储和合成账号；不重放 HAR、不使用其他账号的 Cookie、不发送真实账号安全请求。

## 实际问题与修复

### 第一轮：Cookie 持久化不等于认证完成

- 旧 `AccountSession` 只保存 Cookie 后，加载时可能统一恢复为已登录状态。现在保存真实认证阶段；历史记录没有认证证据时恢复为 `session_candidate`。Cookie 字段名称、数量和分片不判断登录成功。
- 删除 CookieRef 对首次登录资格的错误影响。导入账号的匿名候选先向服务器核实，明确匿名后才开始首次登录；已经完成登录及普通恢复不会自动重登。
- 只有 HTTP 401 或真正空的 `{}` 可表示匿名。非空但缺身份、无效 JSON、身份不符或 5xx 是未确认/错误，不能据此重新登录。
- 登录阶段可以在没有 Set-Cookie 时前进，完整账号记录增加独立 revision。旧 `web_*` 检查点引用新版本记录时同步已保存的真实登录进度，避免重放已提交的邮箱/MFA 步骤；OAuth/grant 的独立检查点不随之重写。
- 原版本的会话交接摘要和引用保持兼容；存储失败时继续保留最新内存快照并阻止后续请求。

### 第二轮：明确拒绝与未知结果分开处理

- 保持已上线的快速路径：完整、明确的 `Factor disabled` 成功回执可靠保存后直接登记新 2FA，不插入停用后 GET，也不伪造只读核实成功。
- 首次重置、恢复及只读核实的初次 `mfa_info` 对 500/502/503/504 最多四轮查询；每轮保存会话。它不嵌套后续状态等待循环，底层连接重试仍有独立预算。401/403、取消、错误正文和保存失败停止。
- 只有完整 HTTP 401、机器码 `recent_auth_required`、与同一 operation/enroll attempt 匹配、且没有任何新登记材料的回执，才开放“验证身份并恢复 2FA”。普通 401、截断、500 和未知登记不能使用该许可。
- 恢复旧任务时 `Input == nil` 曾使显式认证入队 panic；已初始化并用真实 Manager 入队复现后验证修复。

### 第三轮：独立认证与一次性请求边界

- 明确选择认证后，在隔离 Jar 中使用官方重新认证参数；原 Jar、原凭据回调和原检查点不被普通登录逻辑覆盖。必须完成本次密码验证、官方回调，以及实时邮箱和 account ID 核实。existing session 直接跳首页不能冒充重新认证。
- 密码后邮箱挑战保存独立断点，后续点击继续原步骤；不自动重发邮件，也不使用已经失效的旧 TOTP。记录密码/回调的真实时间，另记实时身份核实时间。
- 密码、邮箱和一次性回调先保存 in-flight 标记。未知结果禁止重放；明确未发送或完整机器码拒绝才允许对应步骤继续。
- 实测修复后继跳转未发送却清除已派发前驱标记的问题；保留整条未完成链的前驱，并拒绝已消费后继路径形成的重定向循环。
- 请求发送前标记保存失败时，只在 dirty 内存中记录“明确未发送”的修正；后续必须先保存修正才能发请求。进程丢失后不凭空推断磁盘标记未发送。
- 独立候选的 dirty 状态纳入原重置的账号锁、公开待保存状态和本地 Flush。候选尚未可靠保存时不能释放账号锁，避免其他进程采用旧磁盘 Cookie。

## 采用、重试与收尾

1. 完成独立认证后，保存原恢复检查点；候选证明绑定邮箱、operation、account、原登记 attempt、认证 attempt、密码/回调/身份确认时间和完整候选摘要。它是本地可审计记录，不能替代下一次服务端授权。
2. 在已验证会话中实时确认因子处于关闭状态，才能将旧登记的完整拒绝回执和派发状态存入历史。新的登记使用新的 attempt ID；不知道是否成功的请求不会被改写成“未发送”。
3. 若新的登记再次明确要求认证，下一次用户点击时仅允许轮换与历史采用证明完全匹配的旧候选。先密文归档完整旧候选并读回，再移除 active 候选；任何失败均保留资料并停止新的认证。
4. 同一操作最多保留八次这种已被明确拒绝并完成认证的登记历史，避免无界循环。此限制不影响上一轮成功完成后用户新建的重置操作。
5. 新密钥先可靠保存再激活；激活后仍核实唯一因子与本次 ID 一致。凭据、任务状态和新会话完成可靠交接之后，才清理候选、归档和原 journal。目录按字面名称遍历，包含 `[]*?` 的输出路径也不会漏掉归档。
6. 服务重启只恢复记录与操作入口。普通恢复、只读检查及批量恢复不自动认证；必须由用户明确点击相应入口。

## 用户界面与接口

单账号 `/recover-2fa` 仅在用户确认“验证身份并恢复”时发送 `reauthenticate: true`。服务端再次检查回执与账号绑定；不允许附带新的代理、退出设备、重登授权或上传指令。原有普通恢复和纯本地收尾继续使用原语义。认证中、等待邮箱输入与原会话恢复分别显示，避免认证期间仍提示“不重新登录”。

本次 Cookie 修改属于认证进度与恢复所有权层；标准 Cookie 域、路径、有效期、Set-Cookie 和 Cookie 选择仍由现有 cookiejar 核心负责，没有增加按 next-auth Cookie 名称或分片格式判定有效性的逻辑。

## 边界

本次审查与上线不表示此前失败的真实账号已经恢复。现有 Cookie 可用于身份/状态读取，也可能仍缺少服务端要求的近期认证资格；这是两种不同条件。若官方继续要求邮箱验证码而用户无法获取，程序保留进度并停止，不能承诺跳过官方验证。HAR 中的另一账号只提供接口样本，不能替换当前账号身份。
