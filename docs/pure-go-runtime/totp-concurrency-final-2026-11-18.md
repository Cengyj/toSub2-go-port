## 结论与最终账号状态

1. 两个独立登录会话可以同时有效。B 登录后 A 的受保护查询仍成功，双方身份核对为同一账号，Cookie Jar、HTTP 客户端、凭据与操作目录独立。
2. 本次服务端没有用“已有 2FA”阻止再次登记。A 移除后被 B 抢先设置、A 已判断空状态后被 B 抢先设置，以及双 enroll 重叠，均返回完整 HTTP 200 登记材料。**当前冲突解析器没有被真实冲突触发，不能据本次试验宣布它匹配真实错误。**
3. 顺序激活时双方都能成功，最后接口展示后激活的因子；删除展示项后先前因子重新出现。**`mfa_info` 只返回一个条目，不足以证明账号只有一个有效因子，更不能证明另一密钥失效。** 本次未逐个测试旧密钥的登录能力。
4. 同时激活时，A/B 都收到完整 `200/{"success":true}`。A 的结束查询匹配自己的 F11，提交 K11；B 查询到 F11 而非自己的 F10，于是停止，状态为 `manual_review_required/unknown`，K10 保留为待核对材料。B 的 unknown 来自最终因子不匹配，并非激活响应丢失。

## 根据实测提出的修改建议（尚未实施）

1. **先修正状态语义与日志。** 将“激活回执成功”“当前查询显示本次因子”“本地密钥保存成功”拆成独立字段和时间点。删除“已确认唯一有效验证器”这种接口无法证明的承诺；将 B 的情况写成“激活已获成功响应；当前列表显示另一因子；密钥已保留，后续修改停止”。登录成功应在独立事件中明确显示，token_revoked 应作为脱敏业务码保留。
2. **让普通移除后路径也做结束只读核对。** 当前它凭激活回执便提交，容易让使用者以为远端最终状态已检查。核对失败应保留完整材料及不一致原因，不能丢弃已经可能有效的新密钥；同时说明 ID 匹配仍不能证明其他因子无效。
3. **不要依靠“已有 2FA 会拒绝 enroll”来保证重置语义。** 本次服务端实际接受多个登记/激活。初始状态为空或过时情况下直接登记，不能保证完成了“替换所有旧验证器”。在弄清服务端完整因子清单和删除语义前，应避免自动删除刚发现的另一设备因子或无限回退，保留当前一次回退上限。
4. **保留按操作绑定的多份材料和历史成功。** 存储区分当前已验证、远端已确认激活但未匹配、待确认材料；另一设备变化不应覆盖/丢弃本次 secret。界面展示历史成功时同时给出核对时刻，而非暗示持续有效。现有 pending 与操作 ID 绑定机制应保留。
