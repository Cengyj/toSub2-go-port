## 目标与约束

用户拥有账号和原 2FA 密钥，但不能取得邮箱验证码。可用恢复必须以原任务、原会话、已保存的密钥及阶段为基础；再次点击不得隐式调用新登录。状态未知时保留保护，也必须提供具体的可执行下一步。

设计阶段只读核查；用户随后授权实施。实现和故障测试均使用合成账号，不执行真实账号的恢复、删除因子、登记或激活，不修改线上恢复记录。

## 修改前已确认的问题（历史行号）

1. `internal/protocol/totp_reset_session.go:117` 仅认可无后缀的 `__Secure-next-auth.session-token`。本次本地记录保留的是 `.0`、`.1` 两段，因而被准入校验拒绝。Cookie 保存与传输本身保留原名称；问题是候选会话识别。
2. `internal/protocol/totp_reset.go:146` 在会话读回校验前设置 `disable_intent`、尝试时间及 `old_factor_invalidated=true`。153 行校验失败后，59–100 行错误出口及 `internal/jobs/totp_reset.go:234` 把删除前失败归入未知和隔离。该字段是保守标记，不是官方已删除的事实。
3. `internal/protocol/totp_reset.go:67` 的通用文案掩盖具体校验原因；当前提示不能区分会话格式、绑定冲突、磁盘问题和远端未知。
4. 只修 Cookie 识别仍不足以恢复本次流程：`internal/jobs/totp_recovery.go:102` 还要求 vault 的 pending 与 operation ID 已对应本次；该绑定在 `cmd/tosub2/totp_reset.go:53` 回调中创建，而原校验失败发生在回调之前。是否存在该绑定不能由公共 job 标志替代判断。
5. `internal/protocol/totp_reset_resume.go:112` 只允许匹配已保存新因子的 enabled 状态；旧因子仍在时拒绝继续。当前恢复流程没有“准备已完成但尚未删除”的专用续接路径。
6. 其他单段判断位于 `internal/protocol/recovery.go:82` 和 `internal/protocol/flow.go:551`；特别是 `prepareEnrollmentSession` 在判定不可复用后会调用 `LoginWeb`，因此必须一起处理并给恢复执行器设严格的仅会话模式。

## 第一批：Cookie 兼容与准确诊断

- 将三处会话候选识别收敛到一个纯函数，支持单段 Cookie 及按数值索引排列的 `.0/.1/...` 分段。识别候选不等于验证远端登录态。
- 基于目标 URL 的现有作用域规则核对 domain、host-only、path、secure、partition 和有效期；拒绝编号缺口、空值、异常编号、冲突作用域和歧义组合。给分段数量与总大小设置有文档的客户端资源上限。
- 数值编号连续只能证明本地结构连贯，无法单靠它证明最后一段未丢失；仍需用原会话读取现有账号接口核验身份。
- 不把分段合并后回写为单段，不修改 Cookie 的到期时间。恢复和发送仍使用原始 Cookie 及属性。
- 保留底层结构化原因与错误链，公开日志只输出经过审查的原因码、阶段和安全中文说明，不输出 Cookie、token、密钥、代理认证或上游原始正文。

## 第二批：区分准备失败与修改结果未知

将本地隔离、请求是否可能发出、远端观察结果三个概念分开。建议新 journal schema：

| 阶段 | 证据与允许行为 |
| --- | --- |
| `preparing` / `prepared` | 原会话与身份已保存或正在验证；未进入安全写请求。失败保留会话用于继续准备。 |
| `quarantine_intent` | 正在建立本次 vault/任务绑定；部分失败只恢复本地事务，不发送修改。 |
| `quarantine_committed` | vault 与任务已绑定本次操作并读回；禁止并发修改，但不能据此声称旧因子已删除。 |
| `disable_may_have_been_sent` | 在发送前持久写入的保守边界；重启后只核实，不重放删除。 |
| `disabled_verified` | 同一账号的实时读取已确认停用；允许推进新因子准备。 |
| `enrolled` / `activation_may_have_been_sent` | 已保存完整新密钥和登记信息；激活一旦可能发出，只核实、不重放。 |
| `activated_verified` / `credential_persisted` | 已核实新因子且匹配本次材料；完成凭据保存及本地收尾。 |

发送前写入的边界不代表请求确实发出。只有当前执行明确未进入传输，或传输提供可靠的未发送证据，才可标记未发送；网络超时、进程退出、缺少日志都不能作为此证据。旧 schema 缺少新字段时一律不推断未发送。

准备态须有独立读取校验，不能再要求先设置“旧因子失效”才能验证会话。只有准备快照已原子保存并读回，账号排他锁、vault 与任务绑定都成功后，才进入可能发送边界。所有错误路径保留原会话，准备阶段续接也禁止新登录。

`cmd/tosub2/totp_reset.go:111` 的 operation ID 读取目前也依赖完整会话读取器，影响 Begin、候选密钥保存及提交回调。应把可信私有记录身份读取、会话候选验证、该阶段是否允许修改拆开；读取或完成严格已验证的本地提交不应再次要求 Cookie 当前可发送，但操作归属和密钥一致性不能放宽。

同样的问题覆盖登记和激活：`totp_reset_resume.go:162`、227 行在本地校验或取消检查前就写入 attempted，实际写请求在173、237行。应对 disable、enroll、activate 统一采用“准备/可能已发送/响应确认/读取确认”的证据模型，不能把 attempted 当作已发送事实。

现有 `protocol/totp_reset_abort.go:21` 会回退到 initial 并删除旧 factor ID，后续可能重新进入新登录。优化后，可靠未发送的中止应保留可续接的 prepared 会话、旧 factor ID 和操作身份；元数据、凭据库、UI 都识别这种状态。原凭据快照、独立账号恢复证据和操作归属复核继续保留，不能仅扩大 Begin 的允许操作名。

## 第三批：为当前受影响记录提供真实续接

需要区分“允许只读核实”与“允许继续修改”。本地格式、私有权限、账号/操作/传输绑定可核验且无同账号更新冲突时，允许原会话只读核实；不能因为旧流程尚未写 vault pending，就伪造 pending 或将记录改成成功。

| 原会话核实结果 | 后续处理 |
| --- | --- |
| 仍为记录中的唯一旧因子 | 若有可靠未发送证据，进入专用准备态续接，在原会话中完成当前重置。没有可靠证据时保持只读核实，不因旧因子仍在就自动重复删除。 |
| 已明确停用 | 在检查操作归属、材料完整性及历史登记/激活是否可能发出之后，进入已有停用恢复分支；不再删除。 |
| 已启用本次保存的新因子 | 核对因子 ID 与候选密钥材料，完成提交；不重新登记或激活。 |
| 另一因子、多个因子、身份冲突、返回不明 | 停止修改并保留证据，说明冲突。 |
| 会话被明确拒绝，或需要邮箱验证 | 停止，不启动登录；在无法取得验证且无其他有效原会话时不能保证恢复。 |

当前旧记录的迁移必须锁定原任务，并复核原日志、journal、vault 的操作归属与实时账号状态。诊断为已知缺陷不等于有通用可持久验证的未发送证据；通用迁移不得仅凭 `last_phase=disable_intent` 或缺少某条日志解除隔离。

现有 recover-2fa 的“不登录、不重复移除”语义应保持。建议把只读核实与明确 prepared 的继续动作分别建模；具体接口名是本地实现选择，不是新增官方接口。继续请求应绑定服务端认定的 operation/revision、旧因子、会话和 vault 版本，消费时重新校验并取得同账号排他锁。客户端不能传入 Cookie、任意 factor ID、替换代理或伪造阶段；重复提交返回已有任务或冲突，不创建新的 reset。

用户再次点击时应根据服务端能力进入对应入口。准备续接可以沿用用户原有重置意图；只读检查按钮不能暗中发送删除。确认动作或一次性标识只能限制并发和陈旧请求，不能把“可能已发送”的历史变成“确定未发送”。本次记录若无法建立可靠未发送证据，则只能先只读核实，不承诺自动重新删除旧因子。

## 会话快照和密钥保存

- 已保存、有可发送候选、远端接受、远端明确拒绝、读取暂时失败是不同状态。网络超时或缺字段不能统称会话失效。
- 当前 reader 在副本上忽略 Cookie 本地 expiry，但 `Flow.Restore` 经 CookieJar.Set 会移除过期项；随后保存当前 jar 可能覆盖最后的原始快照。优化应把原始恢复证据与本次执行 jar 分开，不以过滤后的空 jar 覆盖唯一的有效候选记录。不能改 expiry 或自行延长 Cookie，也不能把已被官方撤销的旧 Cookie 自动拿来回退。
- 对已收到的 Cookie 轮换，及时持久保存和读回后再允许后续修改；保存失败保留原记录并暂停。官方已轮换且响应完全丢失的情况仍无法由本地保证恢复。
- 保留现有新密钥登记后、激活前的 journal 与 pending vault 双重保存和读回；远端确认匹配新因子后才能替换有效密钥。新密钥未保存时不激活，已尝试激活后不生成另一把密钥覆盖。
- 已有严格的新因子激活证据并与同一操作的密钥匹配时，继续使用现有纯本地收尾，即使 Cookie 已不可用。未知结果不能转入该分支。
- 不无限保留历史秘密副本。若增加 last-good generation，应设置严格私有权限、受控数量、操作归属和成功提交后的清理规则；保留证据不代表旧会话永远有效。

## 公开状态与用户入口

用结构化状态同时表达以下维度，再映射到简洁中文：

- 失败原因：会话格式未识别、会话不完整、私有记录写入/读回失败、凭据库不可用、操作绑定冲突、远端拒绝、远端结果未知。
- 修改证据：确定未发送、可能已发送、响应确认、读取确认；另存失败阶段，不能只保留统一 recovery_required。
- 会话证据：已保存候选、本地不可发送、远端已接受、远端明确拒绝、尚未核实。
- 可用动作：核实原会话、继续 prepared 重置、恢复停用后的步骤、完成本地保存、当前无法自动恢复。

对于本次类似错误，合理提示为“原登录会话已保存，但分段 Cookie 未通过本地校验；本次停止于删除前准备阶段”，并展示可执行的核实入口。不能以“没有保存会话”代替“会话已保存但程序不认可”；也不能把本地暂停使用旧密钥显示成官方已移除。

新增 `canInspectTotpRecovery` 等独立能力，不让只读入口完全依赖 `canRecoverTotp`。真正会修改账号的继续操作仍由服务端的细化能力和锁控制；普通重登、后台自动修复、导出继续遵守隔离。恢复期间不继承退出全部设备、重登授权、上传等旧选项。

## 并发和一致性

沿用现有同账号锁及跨进程文件锁，不新增平行的互斥体系。只读核实也需保留 reservation，防止读取期间另一轮重置切换因子和 vault。提交前再次核对 journal revision、operation ID、原文件身份、账号/因子 ID 以及 vault 归属；锁冲突不绕过。

准备阶段建立 vault 绑定必须由 manager 的专门转移完成，原子保存、完整读回后再推进；不能在 HTTP handler 直接改 pending，也不能将另一轮 pending 改成当前轮。异常时保留隔离与原证据。旧 journal 不得覆盖较新的有效密钥；重复点击、两个标签页、两个进程和崩溃重启都要覆盖。

## 验收口径

验收目标是：再次点击及重启后使用相同会话、相同任务和正确密钥继续，而不是仅显示失败或关闭按钮。所有测试使用合成账号与可控本地服务；不以真实账号执行破坏性重置作为回归测试。

| 故障场景 | 必须验证的结果 |
| --- | --- |
| 单段及合法 .0/.1 会话 | 候选识别、登录完成判定、准备续接和重启恢复使用同一原会话；发送原始分段 Cookie。 |
| 缺段/空值/冲突作用域/混合形态/超限 | 不错误放行，不删除原始证据，不通过登录绕过。 |
| 完整重现本次：分段 Cookie，Begin 未执行，旧因子仍在 | 新入口可以只读核实；不靠伪造 pending 或跳过门禁；满足证据条件后才允许 prepared 继续。 |
| 准备快照/读回/vault 绑定失败 | 删除请求计数为 0；保留会话与旧密钥，错误准确，修复本地问题后从准备态续接。 |
| 删除成功，响应超时/断连/解析异常 | 远端先实际变更，再注入本地错误；使用原会话只读核实，不重复删除。 |
| 删除成功后落盘失败或真实进程退出 | 重启后保留保守发送证据和候选会话，不用旧 phase 判定未发送。 |
| 停用后登记失败或登记响应丢失 | 区分明确未发送与可能已发送；没有可靠新密钥时不重新登记覆盖未知结果。 |
| 新密钥保存失败 | 激活请求为 0；journal 与 pending 保存状态有准确记录，重试沿用同一材料。 |
| 激活成功但确认响应丢失 | 按已保存的新 factor/secret 核实，激活不重复；提交正确新密钥。 |
| 激活已核实但本地提交失败 | 再次点击只完成同一密钥本地收尾；不需要新登录，会话失效也能走有严格证据的本地路径。 |
| 原会话有效/明确失效/本地过期/仅网络故障 | 分别处理；恢复期间登录、邮箱验证码、退出所有设备的请求计数始终为 0。 |
| 缺新字段的旧 journal | unknown 不默认 false；同时覆盖真实未发送与远端已成功两种旧 disable_intent。 |
| 同时点击、跨进程、旧任务迟到、操作或密钥不匹配 | 至多一个允许的修改流程；不得覆盖新凭据或消费陈旧继续动作。 |

每个关键用例都同时断言：远端因子状态、本地阶段、旧/新密钥、Cookie 内容与轮换、请求次数、是否重新登录或请求邮箱、重启后的入口可用性。对首次重置的登录计数与恢复阶段计数分开记录；恢复阶段 login/email/logout 必须为 0。

### 设计阶段执行的基线验证

以下四项现有测试以合成 fixture 执行通过，包耗时 1.161s，实际命令为：

```sh
go test ./internal/protocol -run '^(TestAuditResetTOTPRemovalAcknowledgedThenJournalWriteFails|TestResetTOTPBeforeDisableFailurePreservesCheckpointAndRestorableIntent|TestReadTOTPResetRecoveryRejectsUnboundOrNonPrivateCandidates|TestResumeTOTPResetRejectsExpiredOrChangedAccountWithoutLogin)$' -count=1 -v
```

1. `TestAuditResetTOTPRemovalAcknowledgedThenJournalWriteFails`：实际先改变模拟远端，再制造 journal 写入失败；确认最后可靠 phase 仍可为 disable_intent。这证明不能只按阶段名解除隔离。
2. `TestResetTOTPBeforeDisableFailurePreservesCheckpointAndRestorableIntent`：证明前置回调失败时不删除且保存 checkpoint；它没有证明再次点击可以完整续接。
3. `TestReadTOTPResetRecoveryRejectsUnboundOrNonPrivateCandidates`：保留身份、权限及文件安全边界。
4. `TestResumeTOTPResetRejectsExpiredOrChangedAccountWithoutLogin`：拒绝明确无效会话或身份/代理变化，不转新登录。

这些是现有安全行为的基线，不能当作分段 Cookie 或新准备态续接已修复的证据。设计阶段未修改功能代码、未重启服务、未操作真实账号；随后实施结果见下节。

还要纠正测试前置条件：已有 manager 恢复 fixture 先成功 Begin，天然具备本轮 vault 绑定；已有快照失败用例只检查远端零修改。新的 runner/UI 验收必须从“Begin 根本未执行”开始，覆盖后续再次点击，不能用预先建立好的 pending 状态掩盖本次故障。

独立会话审查另执行了现有 transport 域/path/删除/分区/响应体中断测试，以及 protocol 恢复绑定/会话拒绝/本地收尾测试，均通过；同样不包含新增分段恢复用例，不能替代上述待新增端到端验收。

## 建议落地顺序与完成标准

1. 先把本次端到端故障做成回归 fixture，补三处 Cookie 识别及安全诊断；不放宽身份或私有文件校验。
2. 在同一个修复批次补准备态、三类安全写请求的发送证据和同会话续接；覆盖 Begin 未执行/部分提交/完全提交，避免只修 Cookie 后仍卡在第二层。
3. 加只读核实与明确可继续的 UI/API，保留现有 recover 不重复删除的约束；旧记录先核实再决定能否迁移。
4. 跑新增协议/runner/manager/UI 故障矩阵、相关 race、全仓测试、vet、前端和生产构建。
5. 验收后按现有本地部署流程备份、排空、升级；对当前账号先做原会话只读核实。任何真实因子修改都必须走通过证据核验的既有授权动作，不能把部署或打开页面当成自动修复触发器。

完成标准是“在原会话仍可用且恢复证据充分的覆盖场景下，用户再次点击能续接，无需邮箱验证”，而不是所有失败都保证可恢复。原会话已不可用、唯一新密钥随响应丢失、请求结果无法判定且无已确认的官方幂等/状态能力时，应明确不可自动恢复的边界。


## 实施记录（2026-11-06）

### 已实现行为

- `internal/protocol/session_cookie_candidate.go`：统一单段与分段 Cookie 候选检查，三处调用共享规则；原始 Cookie 保持原名称及属性发送。缺段、歧义、超限或本地过期不触发重新登录。
- `internal/protocol/totp_reset_state.go`：新增严格 `mutation_schema=1`，disable/enroll/activation 独立发送证据，写前标记可能已发送并读回后才发请求。新格式缺字段或证据矛盾在联网前拒绝。旧格式缺字段不推断未发送。
- `internal/protocol/totp_reset.go` 与 `totp_reset_resume.go`：先保存可信 prepared 会话，再绑定凭据；保存失败、绑定部分失败或传输证明未发送可沿同任务续接。准备续接先核实原账号及唯一旧因子；可能已发送的操作仅核实，不重放。最终失败原因与最近阶段一同落盘，错误链保留，公开说明脱敏。
- `internal/jobs/totp_prepared.go`：将原有效密钥、候选材料及本轮操作绑定为私有凭据基线，只允许同轮事务恢复；拒绝另一轮操作、密钥覆盖或独立恢复冲突。Cookie 过期不会解除 prepared 保护。
- `cmd/tosub2/main.go`：原会话恢复和检查禁止输入密码/邮箱验证码及登录回退；只读检查不进入本地 finalize、不写 vault、不清理 journal。
- 启动恢复：非 prepared 的旧记录如果缺少 journal/vault 任一操作绑定，只重建可见隔离状态，不伪造 pending、不保存凭据、不提交或清理恢复资料；同目录旧密码结果与邮箱迁移也不能旁路写入。已失败任务的时间与原诊断保持，残留登录 checkpoint 不会覆盖它们。
- console 与前端入口：新增单账号“核实原会话”；满足 prepared 证据的任务显示“继续原会话重置”。检查只读，检查成功不显示重置成功、不解除保护；prepared 排除批量重置/恢复。

### 部署校验补充回归

第一次启动的逐文件核验发现：旧流程在会话读回恢复正常之后，启动恢复分支会为缺少本轮 vault 操作绑定的旧记录写入 pending。部署校验因此中止；已停服并以同一安全存储只比较解密结果，确认唯一变化为 pending 标记，密钥及其他字段完全相同。只恢复了本次启动的那份加密文件与元数据变化，保留完整日志和诊断备份。

随后修复启动分支，并新增 `internal/jobs/totp_unbound_restore_test.go`：实际调用 Restore，覆盖分段 Cookie、无操作绑定、既有空 ID pending、同目录密码结果、旧邮箱资料与残留登录 checkpoint。断言零 vault Save、完整凭据与 journal 不变、canInspect=true/canRecover=false/prepared=false，并保留原失败时间和提示。该测试不能用“直接调用 CanInspect 而未重启”替代。进一步覆盖真实顶层旧邮箱字段，并在来源校验、账号锁或文件读取失败时统一阻止邮箱迁移；锁忙下凭据和 journal 字节不变，不能通过迁移旁路写入。

### 当前历史记录的处理边界

此前失败记录没有本轮新增的未发送证据与凭据基线，因此本次更新不自动转换为 prepared，也不自动解除隔离。具备完整原会话及绑定、没有较新凭据冲突时提供“核实原会话”；检查不发送修改请求。仅凭旧因子仍存在或旧阶段名，不自动重新删除。

原会话已被官方拒绝、Cookie 已到期、唯一新密钥随登记响应丢失，或者修改结果未知且现有状态读取无法消除歧义时，仍不能保证无需邮箱即可恢复。实现没有新增或假定未经确认的官方幂等/恢复接口。
