# 回收站自动清理诊断与竞态修复

用户看到“自动清理尚未完成：回收站清理未完成，已保留待清理记录；请检查本地存储后重试”。该提示原本由 `recyclebin.Service.Sweep` 对所有错误统一生成，并不证明发生了磁盘故障。

## 本次运行证据

2026-11-14 的只读检查中，4401 回收站为空，自动保留策略为 1 天。最近检查时间为 `2026-11-14T02:34:52.743035Z`，状态不在运行、无 `lastError`、该轮清理计数为 0。数据目录所在卷可用空间约 203 GB。服务日志没有保存这次自动清理的底层失败原因，之前的回收记录也已经处理完，无法从现有证据确定历史提示到底由并发操作、超时还是短暂存储错误触发。

用户随后确认提示出现在“手动彻底删除或清空回收站后”，与下述已复现的旧快照竞态及旧错误滞留路径吻合。该反馈支持触发条件判断，但不补足已丢失的单次底层错误记录。

本次未手动调用真实账号的清理、登录、重登、上传或外部服务；所有故障复现使用临时目录和合成账号。

## 已复现的问题与改进

- 自动清理读取列表后，手动恢复或永久清理可以使快照中的 ID 消失。原实现将“记录不存在”视为存储错误并停止后续处理。现在使用明确的错误类型，并在重新读取确认该 ID 已消失后跳过。
- 清理与其他账号操作竞争资源时，原实现同样显示存储故障并立即退出。现在仅将明确的忙碌状态延后处理，继续当前批次后续记录；忙碌条目仍计入 20 条尝试上限。
- 原调度器会隐藏超时和失败阶段，账号事务又会将关联缓存错误压成统一英文。现在保留可识别的错误类别，向用户输出固定、安全的阶段说明。底层路径、凭据服务输出和账号信息不会拼入公开错误或落盘的 `lastError`。
- 手动处理完成后，旧错误原本会一直显示到下一轮自动检查。状态读取现在只核对相关记录是否仍存在；已解决的记录错误不再显示，原检查时间与计数保持。全局错误不按空列表清除。
- 页面明确标注“上次自动清理未完成”，增加只读“刷新状态”入口。手动清理失败的响应也保留具体阶段和已进入不可恢复清理的提示。

## 保持的保护

30 秒整轮预算和 20 条上限不变。真正的存储失败、持久性未确认、检查异常或上下文结束仍终止当前轮次；不会跳过失败去丢弃回收记录。永久清理仍先可靠保存 `purging` 标记，再清理所选账号的关联缓存、文件和凭据。删除失败的记录保持不可恢复、可继续处理；未知错误不会泄露私有原因或被当作忙碌忽略。

## 验证

jobs 的回收站测试与 race 检查覆盖消失/忙碌/冲突分类、无副作用拒绝、清理阶段、私有错误隐藏、失败重试和重启后的记录保留。recyclebin 全包 race 测试覆盖快照竞态、忙碌记录不阻挡后续、批次上限、错误优先级与旧状态消除。console 的回收站、短信清理及现有前端回归 race 测试覆盖真实调用链的阶段传递、超时保留、失败响应不可恢复语义以及公开响应不泄露私有数据。
