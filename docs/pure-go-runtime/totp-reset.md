# 设置与重置 2FA

支持入口：[一页排障：用操作日志判断下一步](totp-reset-support-2026-11-18.md)；[激活成功直接保存：修前后请求次数与用户实际日志](totp-reset-receipt-path-2026-11-18.md)。

截至 2026-11-18，本页描述当前实现。并发实验后的变更见 [合入说明](totp-concurrency-update-2026-11-18.md)。旧的独立核实、跨任务远端恢复、验证身份后恢复，以及后来增加的全项目 Cookie 持久化体系已经移除。包括原仓库在内的登录 checkpoint、Cookie 和 session 导出一并移除；每次新操作重新登录，仅使用当次内存 CookieJar。详见 [清理记录](authentication-session-removal-2026-11-08.md)。历史审计文档只用于追溯，不是可用功能说明。

## 当前操作

- 没启用普通 2FA：登录并核对当前账号 → 跳过移除 → 登记新密钥 → 安全暂存并读回 → 激活 → 网站明确接受后，直接提交本地保存。
- 有本次可以替换的旧 2FA：登录并核对当前账号 → 固定旧验证器 → 隔离旧凭据、移除一次 → 按上面的流程登记、激活并保存。用户不用填写验证器 ID。
- 第一次登记明确报“已有”：在同一会话复查。明确未启用就不发移除请求，再登记一次；查到唯一可授权目标且本轮没移除过，才移除后再登记一次。已经移除过、复查仍有因子，不追删。两次登记是整轮上限；模糊提示、超时不触发回退。
- 完成后可再次主动重置，没有次数限制。每次新操作使用新的请求意图，并重新核对当次账号与旧因子；重复发送同一个请求只返回已有结果。
- 每次设置或重置建立新的普通登录流程与内存 CookieJar；等待验证码可在本次操作内继续。没有磁盘登录阶段、共享 account-sessions 仓库、cookie_ref 解引用或逐响应 Cookie 保存 hook。2FA 操作证据不保存可恢复登录会话。
- 活跃任务、未确认的新密钥、身份或操作不一致、同账号未完成操作继续阻止重复修改。

## Linux 与容器的持久化要求

`TOTP_RESET_PERSISTENCE_REQUIRED: 重置 2FA 需要可用的系统安全凭据存储` 表示重置开始前没有可用的持久凭据后端。旧版只支持 macOS Keychain 和 Windows DPAPI，Linux 容器会退回内存存储，因而在创建认证传输、发送远端重置请求之前被拒绝。这个错误不能通过忽略检查或把内存存储标为持久来修复：停用旧因子后，新密钥和确认操作结果的证据必须可以可靠保存并跨重启读取。

Linux 现在可通过 `TOSUB2_CREDENTIAL_KEY_FILE` 指定 32 字节随机原始主密钥文件，使用 AES-256-GCM 同时保护账号凭据和私有 2FA 操作证据。密钥文件需要当前服务 UID 所有、权限 `0600` 或 `0400`；凭据与操作证据分别绑定用途和账号身份。Docker Compose 的 `credential-key-init` 首次初始化独立 `console-key` 卷，主服务只读挂载该卷，加密业务文件继续保存在 `console-data`。这是文件权限保护的外部主密钥方案，部署与备份方式见 [Docker 部署](../go-deployment.md#docker)。

密钥缺失、损坏、不匹配或文件权限不安全时拒绝使用加密存储，不会生成替代密钥覆盖旧资料，也不会在已配置或已绑定的存储上静默退回内存。重置仍保留原有的旧因子隔离、激活前保存待确认新密钥、激活后保存与读回校验，以及已确认结果的本地完成规则。主密钥与数据卷必须配套保留；账号删除不会删除用于读取历史恢复证据的主密钥。

配置好存储后，先核对旧任务状态，再明确发起需要的操作。此前仅在内存保存的密码、TOTP 和 API key 需要在旧进程退出前受控迁移，或升级后重新提供；持久化配置不会自动重发旧任务或恢复登录会话。

## 三种结果与请求边界

| 当前步骤结果 | 后续行为 |
| --- | --- |
| 完整且属于本次请求的有效业务成功回执 | 移除后直接登记；激活后直接提交本地凭据。不再查因子列表，也不重新登录来“试一下”。 |
| 明确业务拒绝 | 仅首次登记明确报“已有”时执行上述一次回退；其他拒绝停止，保留原因。 |
| 超时、断连、截断或兼容解析后仍未知 | 不重复发送可能已执行的修改；移除、激活仅在当次会话中有限只读核实 |

登记仅在新密钥、登记会话及普通因子绑定完整时继续激活。激活成功是网站接受该次登记生成的验证码；不是“查过列表”，也不是“所有旧密钥都失效了”。激活回执丢失或无法解释时才查询列表，核对本次预期因子。查询失败或只显示其他因子，保留已有材料，不当作可用凭据交付，不重新激活或移除。

未知移除只在当前账号的状态明确关闭后推进；未知激活必须对应本次登记的新因子，不能把其他启用因子当作新密钥成功。登记响应丢失而缺少必要材料时停止并说明缺失，不重新登记。读取重用现有有界重试和取消机制；修改请求仅在传输明确证明未发送时重试。

HTTP 200 的 Factor disabled 响应中 passkey_credential_manager_sync 为 null 不影响移除成功。实测同 ID 重叠移除可两边都成功；延迟删除已过期 ID 则出现 400/Invalid request，仍明确停止，不自动改删新因子。登记和激活的在线证据见 [并发实测](totp-simultaneous-removal-2026-11-18.md)。mfa_info 可能只返回多个有效因子中的一个，因此匹配只证明本次查询一致，不能证明其他密钥均已失效。

兼容解析仅处理明确的字段、已知包装及业务语义；新增无关字段、非关键 null 不阻塞。不会递归寻找任意 success/secret，也不会仅凭 HTTP 200、空对象或模糊文案认定成功。

## 本地完成

按钮“完成本地保存”对应 complete-2fa，只允许已存在有效激活证据的任务完成剩余本地工作。流程在创建网络传输之前读取操作证据，核对账号、operation ID、新因子和受保护凭据中的密钥，保存并读回后持久提交任务状态。

这个入口不能登录、读取远端状态、登记、激活、退出设备、重登授权或上传，也不能把结果未知的旧任务变成成功。旧 recover-2fa、inspect-2fa 和 reauthenticate 输入不再提供功能；旧请求拒绝，不能降级成一次新的重置。

新操作使用 activation_evidence_schema=3，要求 state_read、实际复查时间和本次登记材料绑定。只有激活回执、没有通过复查的新记录不能用本地完成绕过检查。历史 schema=2 的 business_receipt 或 state_read 记录仍按原证据读取；兼容不会补造查询确认。完成本地保存本身始终零网络，不依赖 Cookie 交接。

## 中断与历史记录

- 远端已确认、本地保存失败：保留密钥及激活证据，可显式完成本地保存。
- 结果未知、登记材料缺失或证据冲突：保留隔离与操作证据，提示人工处理，不跨任务续接远端操作。
- 服务重启不自动重发修改，不自动释放未知旧记录的隔离。
- 旧版已完成记录即使没有后来增加的提交标记，也不会因此永久禁止新重置：历史任务和已选后续步骤均完成、密钥已保存且无未知操作时，允许用户开始新一轮。此兼容不补写虚假的激活/提交证据；现存未知私有记录和待保存凭据继续阻止修改。
- 不读取或恢复新增框架的共享会话目录。旧 Cookie checkpoint 仅可被识别并拒绝，不能解引用到共享 Cookie、转换为已登录状态或执行自动迁移。旧的已确认 2FA 操作证据仍可只读用于完成密钥保存，不能用于恢复远端会话。
- 本轮按明确授权直接清除项目实际使用目录中的历史 Cookie、登录快照及其副本；混合资料按结构保留合法业务凭据和真实成功证据，无法可靠分类的项列入清理报告。HAR 始终只读。

## 正常可选后续流程

原有退出所有设备、重新登录授权和自动上传选项保留。新密钥保存完成后才执行已选择的退出；退出结果未知不重复退出，也不重复设置或重置。独立本地完成不会补执行这些远端操作。普通账号互斥与旧授权失效规则继续适用。

退出接口沿用原项目的响应兼容规则：正常收到 2xx，且没有 HTML、挑战页或明确错误时判为成功，不要求响应必须是对象或含 `success:true`；空响应、`null` 和数组也可继续已选择的后续步骤。对象中的布尔 `success:false`、真值 `error`、非法或歧义的 JSON 容器仍不能作为成功。网络超时、取消、响应读取失败及 5xx 保持结果未知；本地结果保存失败会报错，已保存的新 2FA 不回退。此规则只用于退出接口，登记、激活和 OAuth 各自的成功证据要求保持不变。

退出成功日志仅表示服务器已接受请求；`/api/auth/session` 仍返回 200、用户信息或新 Cookie 不能证明业务授权有效。受保护接口的 `401/token_revoked` 表示服务端撤销，不等于 Cookie 或 JWT 自然过期。程序不声称已经逐个测量所有设备的失效时间。

## 多验证器登录与密钥绑定

新凭据将密钥与对应 factor ID 一起加密保存。登录优先使用该绑定，且必须在本次服务器返回的 TOTP 列表中存在；验证码验证成功后才确认绑定。旧凭据没有绑定且仅返回一个可选因子时，可在验证成功后补齐。返回多个因子但密钥没有绑定时明确停止，不能凭列表顺序或 mfa_info 猜测，也不会轮流试码。重新导入不同密钥会清除旧绑定。

上述激活后复查适用于产品重置流程的两条分支；历史独立 CLI `--setup-totp` 的原有流程不在本轮重置行为变更范围内。

## 本地验证

只使用合成账号、模拟响应和临时凭据存储。既有测试同时断言结果、请求顺序与次数，覆盖两条重置分支的激活后只读核对、未知路径无重复修改、账号和因子不匹配、关键材料缺失、保存失败、旧入口拒绝及本地完成零建连。旧完成记录通过单个和批量入口连续四轮模拟提交/完成/重启，验证可重复重置与同意图不重复入队；这不是对真实账号执行重置。

Linux 持久化验收还需要使用真实文件后端验证跨进程读回、密文及身份校验、密钥丢失和权限错误的拒绝行为，以及加密操作证据支持本地完成且不重复远端修改。容器健康检查只说明服务已启动，不能替代这些测试或证明当前线上账号流程成功。
