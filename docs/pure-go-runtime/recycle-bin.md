# 账号回收站与永久清理

更新日期：2026-11-03。本文说明当前代码的使用方式、业务契约与运维影响，不表示现有运行实例已经升级。部署与浏览器验收结果应以对应交付记录为准。文中的路径、邮箱和凭据均为示例。

此前实现的范围、测试、构建与验收边界见 [2026-11-03 实施记录](recycle-bin-2026-11-03.md)。后续界面和可靠性改动的验证、部署状态由对应交付记录另行说明。

## 删除、恢复与永久清理

账号列表的删除操作现在默认将账号移入回收站。兼容入口 `POST /api/jobs/delete-batch` 同样执行软删除；旧响应中的 `deleted` 计数表示移入回收站的账号数，不能解释为凭据或文件已销毁。

回收站可通过侧栏导航进入，也可使用账号管理页标题旁的次级“回收站”按钮；窄屏时该按钮与全量用量刷新一起排列在标题下方。入口只切换页面，不执行删除、恢复或永久清理；查询功能关闭时回收站入口仍独立保留。

回收单位是规范化邮箱对应的完整账号历史。同邮箱的多个任务记录一起移出活动列表，并保留在一个回收条目中。回收条目数与内部历史任务数可能不同。邮箱比较忽略首尾空格和大小写。

| 状态 | 可执行动作 | 数据处理 |
| --- | --- | --- |
| 活动账号 | 现有账号操作，受原资格与互斥规则约束 | 沿用现有存储 |
| `trashed` | 查看回收信息与历史日志、恢复、明确永久清理 | 保留账号历史、文件和私有凭据 |
| `purging` | 查看清理状态、重试完成永久清理 | 已开始不可逆清理，剩余数据保留用于重试 |
| 永久清理完成 | 无恢复入口 | 选中账号的本地数据与凭据已完成清理 |

软删除先取得同邮箱操作门禁，安全暂停 SMS 等外部资源的本地所有权，再取消任务与只读查询，等待已有任务和查询租约退出，最后原子保存回收条目。不能把“请求已受理”或“正在取消”当作已经回收。取消、写盘失败或响应中断时，应重新读取列表与回收站核对实际状态。

同邮箱仍在回收站中时，导入被拒绝，包括改变大小写、两侧增加空格和重复使用原私有任务 ID 的方式。用户应先恢复原账号，或明确完成永久清理后再导入，避免同邮箱共享凭据被覆盖或误删。

## 回收站页面

回收站提供以下浏览方式，筛选和排序不改变账号数据：

- 搜索邮箱、回收记录 ID 或任意历史任务 ID；忽略输入首尾空格与大小写，按包含关系匹配。
- 状态可选“全部状态”“可恢复”“清理未完成”。“可恢复”同时要求条目处于 `trashed` 状态且后端允许恢复；“清理未完成”对应 `purging`。
- 排序可选“最近移入优先”“最早移入优先”“即将清理优先”。默认最近移入优先；按清理时间排序时，无明确到期时间的条目排在有到期时间的条目之后。
- 列表每页 20 条，显示匹配数量、当前范围与翻页按钮。当前实现先读取完整回收列表，再在浏览器中搜索、筛选、排序和分页，不是后端分页。改变搜索、状态或排序后回到第一页；记录减少时页码自动调整到有效范围。

“选择本页”只作用于当前显示的记录。翻页或修改筛选、排序后，其他页面或已被筛选隐藏的选择仍然保留；页面会显示已选总数及其中不在当前页的数量。批量确认框也会提示隐藏选择，执行前应核对完整范围，必要时点击“清空选择”后重新选择。选择仅保存在当前页面组件中，不是浏览器持久化偏好；刷新读到条目已移出回收站时，会移除该条目的选择。

批量恢复要求所有选中条目均可恢复；混入 `purging` 或其他不可恢复条目时，恢复入口禁用。可先清空选择，再筛选“可恢复”并选择需要的记录。`purging` 行提供“继续清理”，不提供恢复；该动作继续同一条目的永久清理，已经不存在的文件或私有记录按幂等方式处理。

“详情与日志”打开独立详情弹窗，展示回收状态、移入时间、保留策略、回收记录 ID 和最近操作错误。选择历史记录后可查看相应任务的操作类型、状态、ID 与日志，存在更早记录时可继续“加载更早日志”。账号列表的 20 条分页与日志游标分页互相独立。查看详情或日志不会恢复账号或重放任务；记录被其他页面恢复或清理后，详情会提示该记录已不在回收站。列表读取失败时，详情明确标注所展示的是最近读取的信息。

读取列表失败会保留最近成功的列表并暂停恢复、永久清理等写操作。写操作结束后，须重新读取并核实列表才能继续下一次写操作；请求超时或断开不会自动重放。确认提交前还会复核记录与资格，状态发生变化时要求先查看最新列表。后台清理进行中也会暂时阻止冲突操作。永久清理确认范围为本地账号资料、授权文件、凭据及历史日志，不删除 Sub2API 远端账号。

## 保留范围

软删除不移动或销毁以下资料：

- 根任务元数据中的账号历史、工作流状态及回收条目。
- `<data-root>/<job-id>/` 下的授权结果、原始资料、checkpoint、一次性结果恢复文件及其他既有私有产物。
- 邮箱对应的安全凭据，包括当前密码、2FA 密钥、代理资料及待恢复安全操作标记。
- `account-insights/` 中的历史用量、订阅和权限观察缓存。
- SMS 私有记录 `sms-job-<job-id>`；恢复记录增加 `trashPaused` 标记，原订单、已见验证码和待处理动作作为私有归档保留。
- 已保留的操作日志。完整保留历史由根元数据中的最近 200 条摘要与 `<data-root>/<job-id>/operation-logs/` 中的独立私有归档组成。新记录挤出摘要前先原子归档，回收前再归档当前摘要；读取按稳定游标每页最多 500 条，可继续加载更早记录。旧式重复纯文本也保留次数，损坏的归档不能被当作保存成功。旧版本已经裁掉、磁盘上也不存在的日志无法补回。

私有凭据仍由现有安全存储保护，不复制到普通 JSON、日志、测试或文档中。回收站 API 不提供真实密码、Cookie、token 或 SMS 平台密钥。备份时必须把回收站当作仍含完整敏感数据的区域。

查询服务分别使用活动账号集合和保留 ID 集合：活动集合决定请求、轮询、状态与查询资格；保留集合只保护缓存免于孤儿清理。回收站账号不会因为保留了缓存而得到查询资格。已取消的查询直到实际释放传输租约才不再计为执行中，迟到结果不能覆盖已保存的历史缓存。

恢复账号后，历史缓存仍受原授权修订号校验；授权或账号修订变化时，旧观察不会伪装为当前有效结果。磁盘上的保留历史不因此被删除。

## 恢复不重放历史操作

恢复只把回收条目重新放回活动账号集合，不进行登录、重新授权、refresh token 轮换、2FA 重置、退出设备、上传或原 checkpoint 的自动执行。未完成的恢复和自动同步保留暂停标记，需在原操作入口明确继续并通过现有资格检查。原授权方式和已安全保存的结果保持不变。

恢复和重启都不安装 `trashPaused` 的 SMS 会话，不提交旧 OTP，也不重放保存的 `release` 或 `complete` 动作。重新使用接码需要用户明确配置新的接码操作。软删除不会调用供应商的 Release/Complete；正在取号或完成订单的账号暂时不能回收，需等待已有动作返回后重试。

暂停 SMS 时先安全保存带 `trashPaused` 的记录，再撤销本地所有权和取消轮询。保存失败会保留原私有记录并阻止回收成功；错误信息不包含原始凭据错误。批量暂停中已保存的暂停记录也保留，避免因失败回退而盲目恢复外部动作。

既有只读用量查询仍由原查询开关、间隔、排除项和授权资格控制。恢复本身不会直接发起上游查询；恢复后若原自动查询计划启用且账号符合资格，后续计划仍可能进行只读查询。

## 自动保留天数

策略位于 `<data-root>/recycle-bin-settings.json`，通过回收站设置入口读取和保存。使用带 revision 的更新，另一页面已修改时必须重新读取，不能静默覆盖。

从回收站顶部“保留策略”进入设置。该设置属于当前本地服务，由使用该服务的浏览器共享，不是单个浏览器的偏好。输入框中尚未保存的天数只用于预览；“放弃更改”恢复最近核实的服务端值，不写入服务端。“重新读取配置”重新获取服务端策略，并重置未保存输入。

- 默认 `retentionDays = 0`：不因到期自动发起新的永久清理。
- 可配置 `1–3650` 天；非法值不保存。
- 到期时间为原 `deletedAt` 转为 UTC 后，加上 `retentionDays × 24 小时`，按实际经过时间判断，不是本地自然日的午夜。
- 不使用 OpenAI 请求时区替代回收时间语义；夏令时、浏览器时区和跨日显示不改变实际到期时刻。
- 当前策略作用于已有回收条目，不会在修改策略时重新开始计时。缩短天数可能使已有条目立即到期；增大天数会延后尚未开始清理的条目。
- 自动任务启动后检查一次，之后按分钟检查；策略更新会唤醒检查。每轮有时间预算与数量上限，不保证在到期瞬间完成清理。
- 一旦条目已经持久化为 `purging`，即使随后把天数改为 `0`，仍会继续重试已明确开始的清理。关闭自动到期不能撤销已经开始的永久清理。

界面将 `0` 显示为“持续保留 · 自动清理关闭”。从 `0` 启用正数保留天数、缩短保留期限，或重新确认持久性未确认的正数策略时，会要求确认已有过期条目可能立即永久删除。修改输入不等于策略已生效，必须完成保存。

保存发生版本冲突、网络中断或结果未知时，设置区域先阻止继续编辑和保存，需“重新读取配置”后再核对。服务端若仍报告持久性未确认，显示“自动清理暂停 · 需核实并确认”，需修复存储并点击“重新确认保存”；仅重新读取或放弃输入不等于确认策略可靠保存。回收操作进行中或其结果尚未重新核实时，设置也不能编辑或保存；策略正在保存时，回收操作暂不可提交。配置保存的核实门禁与回收操作的列表核实门禁分别处理，不能将任一“已读取”提示当作所有操作均已确认。

示例：合成账号在 `2026-11-03T08:00:00Z` 移入回收站。保留 7 天时到期为 `2026-11-10T08:00:00Z`。在 11 月 8 日改为保留 3 天，原到期点为 11 月 6 日，下一轮检查就可能开始永久清理；不会从 11 月 8 日再加 3 天。

策略文件不存在时才初始化默认策略。已有文件必须提供受支持的 `schemaVersion = 1` 和正数 `revision`；缺少或置为 `null` 的版本字段、空对象、整个文件为 `null` 等情况不会用默认版本补齐后继续运行。具有有效版本字段但未填写 `retentionDays` 的文件仍按 `0` 保守处理，非法天数则拒绝。

策略文件无法读取或校验失败时，不启用到期清理；控制台会将回收站功能标为不可用，并保留阻止不安全删除的保护入口，不回退为直接永久删除。应从有效配置或备份核对并修复，不应直接删除损坏策略来抹去原配置意图。保存已经替换文件、但目录持久性未确认时，显示结果未知并在当前进程暂停自动清理；修复存储后重新读取并明确保存，不能把“有新值”当作已经可靠保存。核实前不要直接重启：新进程会读取磁盘实际留下的策略；一次未确认的替换可能留下旧值或新值，内存中的暂停不等于已经形成可跨崩溃确认的策略。

如果回收操作尚待核实，切到保留策略页后可点击“核实回收站状态”，直接重新读取列表；读取期间防止重复请求，错误明确显示。只有成功取得权威列表后才解除该门禁，不需要反复切页，也不会自动重放恢复或永久删除。该按钮不替代策略保存结果的“重新读取配置”。

## 永久清理与失败恢复

永久清理必须明确确认。服务先持久化 `purging` 墓碑，再清理本地缓存、SMS 私有记录、账号目录和账号凭据。邮箱级门禁与同邮箱/同 ID 所有权检查阻止在清理过程中恢复、重新导入或误删另一活动账号的凭据。

用量缓存的显式清理只针对选中 ID 的哈希缓存文件，活动账号或未释放的查询票据会阻止清理。SMS 清理只删除相应 `sms-job-<job-id>` 私有记录，不调用供应商接口，也不删除共享自定义号码池 `sms-pool-*`。

任一步骤失败都会保留 `purging` 条目和可诊断的安全错误，不能恢复已经部分删除的账号。修复权限、磁盘、凭据服务或未结束的本地操作后，重试同一条目即可；已经不存在的文件/私有记录按幂等清理处理。不要手工删掉墓碑以绕过失败，否则保留目录可能被扫描恢复为活动账号。

自动清理每轮保留 30 秒预算、最多尝试 20 条记录。若列表快照中的记录已被手动恢复或清理，后台会再次核对其确实已不在回收站，然后跳过；账号操作仍占用资源时暂缓该条并继续本轮后续记录。真实文件、凭据或持久性错误仍停止本轮。提示区区分操作占用、超时/中断、元数据保存、历史文件检查、用量缓存、模型检测缓存、短信数据、账号文件及安全凭据清理，不再将所有失败都归因于本地存储。

提示区显示的是“上次自动清理未完成”，其中“刷新状态”只读取列表，不重放永久删除。某条记录对应的失败已通过手动处理解决时，下一次状态读取就会停止显示这条旧警告，保留原检查时间与清理计数。策略持久性未确认、全局文件检查或上下文中断等错误不会仅因列表为空而隐藏，须核对相应问题或等待后续成功检查。具体排查与验证记录见 [自动清理诊断优化](recycle-bin-cleanup-2026-11-14.md)。

看到超时或网络断开时，先刷新回收站核对状态，再决定是否重试。客户端不能对有副作用的请求自动盲目重放。不要通过真实账号登录、重登、刷新、2FA 或上传来验证清理结果。

## 部署、备份与恢复

构建、平台支持与现有启动方式见 [本地运行说明](../local-macos.md) 和 [部署核验记录](local-deployment.md)。继续使用纯 Go 服务、Go esbuild 前端和现有安全凭据存储，不新增独立运行时。

部署前应建立维护窗口并阻止新任务进入，确认账号任务、SMS 取号/订单动作、只读查询、巡检和回收清理均已排空。保留旧程序与静态资源摘要，优雅停服后备份整个私有数据根及所需安全凭据恢复材料，再原子替换程序。不能只备份活动账号目录。

回收服务的关闭流程会先拒绝新操作，取消自动任务，并在停服 context 的时间预算内等待已进入互斥门禁的配置写入或清理操作结束，再确认后台任务退出。这个等待也覆盖未启动后台任务时已经受理的写入或直接清理。关闭超时返回错误，不能当作安全停服完成；已受理的操作可能仍在结束过程中。维护流程应确认服务实际退出及数据状态一致后再备份或替换程序，不能仅凭停服请求已发出继续后续步骤。

备份至少包含：

1. 根 `job-meta.json`，包括活动账号、`trashed` 与 `purging` 状态。
2. 全部账号目录、checkpoint、授权结果与 `operation-logs/`。
3. `account-insights/`、`recycle-bin-settings.json` 及其他原配置。
4. 现有凭据 namespace 对应的安全存储与恢复所需密钥材料；按原平台凭据规则处理，勿导出为明文。

示例备份根使用 `<private-backup-root>/before-upgrade/`。目录应仅当前运行用户可访问，文件保持原私有权限；不要把备份、HAR、私有配置或真实凭据加入源码/Git。复制完成后核对完整性。

恢复备份必须停服并整体恢复同一时间点的元数据与私有文件，避免用旧元数据搭配新授权结果。优先在独立临时目录用合成账号验证恢复程序；真实恢复应先保留现状副本，并确认不会覆盖升级后取得的一次性授权或新的2FA密钥。

部署后只读核对健康、运行二进制摘要、嵌入前端资源、回收站策略、活动与回收条目数量及暂停状态。不要为了验收点击真实账号的有副作用操作。恢复自动计划前说明：非零保留策略可能立即清理已到期条目，已有 `purging` 会继续完成本地清理。

## 回退限制

**回收站非空时不能直接使用不认识回收站的旧程序打开当前数据目录。** 旧版本可能忽略墓碑，再扫描保留的账号目录，把已回收或部分清理的账号复活为活动账号。即使旧二进制能够启动，也不等于数据格式兼容。

即使回收站已经为空，也必须检查恢复出的活动记录是否带有 `recovery_paused` 或 `auto_repair_sync_paused`。旧程序忽略这些暂停标记可能恢复历史流程或自动同步；“回收站为空”本身不是只替换旧二进制的充分条件。

安全选择包括使用已经理解回收格式的兼容版本，或在维护窗口内由当前版本处理所有回收条目，并核对没有 `purging` 残留后再评估旧版本兼容性。选择恢复还是永久清理属于真实数据决策，不能为了回退方便自动执行。

必须回到升级前完整备份时，应单独确认会丢失哪些升级后的变化；保留当前完整副本，停服后恢复一致的数据与凭据，不把“只替换旧程序”视为跨回收格式的安全回退方案。

## 卸载与验证边界

普通卸载程序或移除自启动不等于删除账号数据；软删除同样不等于隐私销毁。彻底卸载需要先确认是否保留备份，停服并解除自启动后，按照现有卸载文档处理完整数据根、回收条目、日志、缓存和对应安全凭据 namespace。共享号码池只在明确卸载整套应用时按原规则处理，不能被单账号永久清理顺带删除。已另存的备份、日志导出和回退材料需要单独处理。

回归验证应使用合成邮箱、模拟服务和 `t.TempDir()`，覆盖查询缓存软删/启动保留、查询迟到结果、明确永久清理与失败重试、SMS 暂停保存失败/取消、取号或订单完成并发、恢复不重放旧 OTP/远端动作、共享号码池保留，以及无效策略拒绝和关闭时等待已受理操作。界面验收还需核对跨页选择、筛选、详情与历史日志、配置草稿及未确认结果门禁。

具体测试命令与执行结果、完整工程回归、平台构建、浏览器交互及正式部署状态由对应交付记录说明。交叉编译不等于原生平台验证，构建成功也不等于交互与视觉验收完成；本文不声明性能提升，也不把之前部署结果算作本轮已部署。
