## 二、重置决策：证据足够就推进
1. 明确没有普通 TOTP：跳过移除，在已核实身份的原会话直接登记。仅缺可选状态字段时，有界只读复核；仍满足既有安全条件，可以尝试一次初次登记。“允许试登记”不等于“已证明未启用”。挑战页、认证错误、恢复因子、损坏的响应不能当成无 2FA。
2. 已有本次获准替换的普通旧因子：绑定目标 ID，只移除一次。完整且已可靠保存的明确移除回执足以继续登记，不为无关字段或冗余查询把账号卡在“旧已移除、新未设置”。移除结果不明时先只读核对；若后置条件足以继续，记为“由状态核对确认”，不要伪造成功回执。
3. 初次登记明确被“已有 TOTP”拒绝：优先认端点业务码，其次才认有夹具支持、语义无歧义的完整文案。保存初次回执，原会话只读定位；确认为本次获准替换的旧因子时，自动执行最多一次移除、一次正式登记，不要求用户从头重跑。裸 409、模糊文字、否定句、矛盾响应都不是删除授权。无法确认目标时，告诉用户具体需要核对什么。
4. 旧因子已移除后正式登记再次冲突、旧 ID 已过期、或出现另一设备的新因子：不再进入初次回退，不换目标追删。突出显示“旧因子移除已有证据，新因子尚未确认”，不能笼统写“登录失败”或“请重试”。
5. 分清确定未发送、可能已发送、收到完整回执。超时、断线、截断、5xx、429 和认证拒绝分别处理，写操作结果未知时不自动重发。只读重试有预算、退避、截止时间且可取消。明确撤销或需要重新认证时停止该会话的写操作，不偷偷补登录。可选退出只在用户已选且重置可靠完成后执行一次；退出失败不抹掉重置成功。

## 三、按阶段使用最小充分证据
- 移除：完整、与目标绑定且无矛盾的成功响应中，已识别的 “Factor disabled” 即可证明移除回执，不强求同时有 success。登记：必须有可用的新密钥、登记 session_id、可信的普通非恢复 TOTP 因子 ID（HAR 为 factor.id）。先保护并读回 pending 材料，才允许激活。登记会话不等于登录会话，拿到密钥不等于启用成功。
- 激活：完整可信的 2xx 中，无矛盾的 success:true 或已支持的等价信号即可确认激活回执，不要求回显整份登记对象；若回显绑定则必须匹配。回执不明，但派发证据、已保存的登记绑定与同账号只读状态足以确认时，可按“只读核对确认”推进，不补发激活。logout 的 200/null 只表示退出请求已接受，不能套用到激活。
- 远端回执、因子匹配、本地提交分别记录。多个可见因子里能明确匹配本次 ID，与“有权移除哪个目标”是两个判断。只显示另一 ID 时，保留已获回执和 pending 材料，不宣称本次密钥无效或账号只有一个验证器。远端已匹配但本地保存失败，恢复时只补本地提交，远端写入为零。
- 兼容字段顺序、空白、已知无害扩展及明确等价的可选表示；不吞掉业务错误、重复的关键字段、类型错误或绑定冲突。原回包与脱敏回执读回后的业务分类必须一致，不能通过投影丢掉矛盾字段。凭据读回只归一化确实等价的值；密钥、因子、操作绑定或非空邮件头实质变化必须报错。保留写前意图、pending/current 隔离、受保护存储和旧 journal 兼容性。
- 保持职责清晰：协议层解释回执，工作流依据证据选择下一步，凭据层负责安全写入和读回，日志与界面只展示结果。恢复决策以绑定的 journal、凭据和只读核对为准，不从日志反推。复用现有类型和入口，不平行新建一套状态机。

## 四、把日志作为可验收的产品功能
1. 追通完整链路：internal/protocol/flow.go 的事件 → cmd/tosub2/job_runner.go → jobs.JobEvent → internal/jobs/operation_state.go 的 appendOperationLogLocked → internal/jobs/log_archive.go → 控制台 API、web/src/components/job-logs.jsx、复制与下载。当前 JobEvent.Data 不会自动完整进入 LogEntry；消息会截到 512 个字符，连续相同记录会去重，超过 200 条进入归档流程。验证字段真正到达用户能看到的地方，不把 JSON 塞进中文消息，也不另建日志平台。
2. 每次操作用不含秘密的本地关联号 op_ref，每次请求另有 attempt_ref，操作内用 seq 排序。区分本次与历史、只读与写入、产品动作与测试观察。按阶段记录适用字段：阶段、方法和路径模板（无查询串）、起止时间、耗时、派发状态、HTTP 状态、回执完整性、脱敏业务码、证据来源、判断原因 reason_code、下一步 next_action。显示北京时间及偏移，耗时用单调时钟；没有 HTTP 响应就明确记“未收到”，不编造状态码。
3. 记录每个关键判断的理由：为何直接登记、为何回退或停止、还剩几次只读尝试、回包缺哪个白名单关键字段或其预期/实际类型、预期因子与可见因子是否匹配、本地失败在写入/读回/最终提交哪一步。因子用操作内代号 F1/F2，不打印原值。正常进展一句中文即可；异常给出中文摘要、稳定原因码和可执行的下一步。关键原因在默认日志可见，不依赖 debug。
4. 每轮有一个可识别的终态摘要：最后可信步骤、旧因子移除证据、新材料是否已保护、激活证据、因子核对、本地提交、可选退出、各写步骤的次数及安全下一步。没有可靠发送证据时写“可能已发 1 次，未获确认”，不要写 0 次或已成功 1 次。未执行、明确失败、结果未知和不适用不能压成同一个 false。崩溃后恢复延用同一操作关联号并注明证据来源。CLI、API、界面共用同一判断，不靠解析中文文案决定业务状态。
5. 合成示例：中文摘要“服务端已确认激活；本次预期 F2，当前查询仅显示 F3。待核对密钥已安全保留，未再次激活或移除。下一步：核对因子绑定。”对应详情：{"op_ref":"O7","seq":9,"stage":"verify_factor","reason_code":"EXPECTED_FACTOR_NOT_VISIBLE","activation_receipt":"accepted","expected_factor":"F2","visible_factor":"F3","pending_readback":"verified","local_commit":"not_performed","next_action":"review_binding"}。另给“正常完成”和“远端已匹配、仅需本地补保存”的示例。
6. 诊断字段采用白名单，未知业务码映射为稳定类别。密码、邮箱原文、Cookie、token、验证码、恢复码、密钥、otpauth URI、原始请求响应和头信息不得进入普通日志、错误链、详情、复制或导出；不能用验证码或密钥的裸哈希做关联号。普通日志写失败可告警，不得触发新的远端修改；受保护 journal 的关键意图、回执或凭据不能持久化时，则须在下一次修改前停止。重复只读可聚合计数，不得吞掉不同写尝试、首个失败、阶段变化和终态。

## 五、验收与交付
1. 用假传输、独立合成 A/B 上下文、临时存储和可控时钟回归五组历史输入：移除后状态变化、判空后状态变化、双方各自收到登记/激活回执、同目标移除与过期 ID、退出后会话信息与业务授权不一致。需要控制时序时用事件屏障，不靠 sleep 猜测。统计假传输实际收到的请求，不用日志条数当请求数。不重新制造真实账号竞态或探测旧凭据。
2. 硬性计数：无旧因子的成功路径＝移除 0、登记 1、激活 1；明确初次冲突且目标获准的成功路径＝初次登记 1、移除 1、正式登记 1、激活 1；冲突含糊或目标变化＝新增移除 0；激活结果未知＝追加激活 0；存储预检失败＝远端修改 0；只差本地提交＝恢复期间远端写 0。另测完整响应后才发生的传输错误、截断、存储故障、撤销、取消及重启。
3. 日志做端到端验收：从正常入口注入合成故障，只给验收者界面复制出的脱敏日志，不给 HAR、数据库或密钥。他应能找出操作号、最后可信步骤、相关请求及结果、是否有重复写、停止原因和安全下一步。验证超过 200 条后的归档与分页、长错误、相同阶段不同尝试、同账号不同轮次、旧格式、复制与下载。向错误消息和响应扩展注入合成敏感标记，断言日志、API、详情和导出都无泄露；普通日志故障不改变业务结果。
4. 交付实际代码、回归测试、事件字段和原因码说明、一页排障指南。先跑受影响包和前端日志测试，再跑适用的离线 go test -race。用一张表报告“证据来源 → 修前 → 修后 → 用例及实际请求次数 → 用户可见日志 → 剩余风险”，附命令、通过/失败/跳过项、旧记录兼容与回滚影响。未验证就写未验证；引用历史账号状态、安全保存位置或撤销区间时注明归档时点和观测边界，不称为本轮线上验证。
