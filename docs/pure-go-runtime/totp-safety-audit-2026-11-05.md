## 审查结论与范围

原先对精简停用响应和短暂状态延迟的处理已经改进，但当前实现仍不能保证旧因子移除后不会中断。普通重置存在恢复会话及登记材料缺口；实时账号身份验证还存在缺失信息时继续放行的分支；首次设置也没有采用重置流程同等严格的状态确认。

本次审查覆盖协议、任务管理、控制台和生产 runner，并使用合成账号及模拟传输验证。没有对真实账号执行移除、登记、激活、退出或恢复操作。本轮交付是审查记录，未修改业务代码、未重新部署服务。以下“建议”均不是已经实现的能力。

审查时 4401 监听进程为 PID 65153，安装二进制 SHA-256 为 `5f71c8a91f7eb5887ffbdf20fdfacc9d9dd4843fcc0783554a35a6c3e273c3cf`，与此前状态同步修复的部署记录一致。存在 `RecoverTOTP` 源码不代表控制台已提供自动恢复；搜索非测试 Go 调用点仅命中该方法定义。

## 需要优先修复的代码缺口

### P1：首次设置允许仅内存保存的新密钥进入激活流程

- 位置：`cmd/tosub2/main.go:158–166`、`:570–573`、`:641–675`。
- 安全凭据存储初始化失败时 runner 回退到 `MemoryStore`；首次设置只检查 store 非空，并在 `durableCredentials=false` 时把私有结果路径清空，仍调用 `SetupTOTP`。登记回调和最终保存因而只写内存。
- 影响条件：进入这一降级分支且远端激活成功后，进程退出可能丢失本次生成的唯一密钥。普通重置已有持久化前置拦截，首次设置需要同样限制。这里没有断言当前 4401 正处于内存降级模式。
- 建议：首次设置在任何登记/激活请求前要求可用的持久凭据库和恢复 journal；新密钥写入后读回验证。不应以启动时的一条警告替代禁止高风险操作。

### P1：缺少实时邮箱证明时仍允许重置或恢复

- 位置：`internal/protocol/totp_reset.go:336–371`，`currentTOTPAccount`。
- 当前仅在会话恰好提供非空 `user.email` 时检查它是否匹配所选邮箱。会话缺少邮箱但含 account ID 时仍放行；会话 HTTP 401、403、500 且没有传输错误时，还可以退回网页 token 中的 account ID。
- 本地模拟已证明：缺少邮箱的会话可完成整个普通重置和专用恢复；会话读取被拒绝时仍可从模拟 token 获得另一 account ID。
- 影响条件：若所持会话与所选账号意外不一致，这个边界无法证明被操作账号确属目标邮箱，存在操作错误账号并把密钥记到所选账号下的风险。这不是已证实发生过的真实串号，也不意味着拥有 account ID 即可绕过上游认证。
- 建议：要求成功、可验证的实时身份响应及目标邮箱匹配；缺失、冲突或拒绝均在任何安全写请求之前停止。不得把本地 checkpoint 的邮箱标签代替远端身份验证。

### P1：普通重置删除普通 checkpoint，却未保留专用恢复会话

- 位置：`internal/protocol/totp_reset.go:149–154`、`:74–77`。
- 发送移除前删除普通登录 checkpoint，失败路径再次清除；当前进程内 Cookie Jar 仍能继续使用，但没有对应的独立持久恢复会话。
- 若旧因子已移除，随后服务退出、进程崩溃或流程结束，可能丢失原本还能用于核实及完成绑定的会话，恢复时需要重新认证，可能再次需要邮箱码或当前有效因子。
- 建议：修改前保存账号绑定的私有恢复会话，隔离于普通登录发现路径；保存失败则不移除。会话恢复后仍要验证身份和实时因子状态。不能直接保留普通 checkpoint 并允许普通任务复用，也不能保证恢复会话永不过期。

### P2：普通重置未完整保存登记意图及部分登记资料

- 位置：`internal/protocol/totp_reset.go:181–199`。
- 普通重置发送 enroll 前没有独立的 `enroll_intent`；返回材料全部通过校验之后才保存新密钥和因子 ID，且 journal 不保存 `session_id`。
- 模拟 enroll 返回合法 secret、session ID、new factor ID，但缺少 `is_recovery`：激活被正确阻止，但这些已收到的恢复字段也全部没有进入 journal。旧因子此时已移除。
- 影响：保护性停止是正确的，但恢复证据不足，无法准确区分“未登记”和“登记请求已发送但结果不完整”，也不利于受控恢复。完整正常回包后保存的新 secret 并不会因此全部丢失。
- 建议：发送前持久化 intent；回包后先私有保存可识别材料，再验证是否允许激活；同时保存 session ID。可借鉴 `internal/protocol/totp_recover.go:119–150`。资料存在仍不能授权盲目重发 enroll/activate。

### P1：首次设置的状态确认弱于重置

- 位置：`internal/protocol/flow.go:1390–1493`；生产调用为 `cmd/tosub2/main.go:641–680`。
- 首次设置没有调用重置所用的实时账号身份核验；使用 `!hasTOTP(info)` 决定继续，未知/缺失字段与明确停用未区分。
- 激活回包 `success=true` 后，实时状态读取失败或仍未启用只发 warning，仍返回成功；没有核对本次新因子 ID。生产 runner 随后将 secret 提升为正式密钥并更新已启用状态。
- 影响：激活 ACK 是重要证据，但不能证明当前唯一生效因子就是这次保存的密钥；在响应不一致或并发修改场景，可能过早宣告完成。首次设置不会主动移除原因子，但不应因此降低身份和最终确认要求。
- 建议：与重置统一身份确认、明确停用判断、登记意图、材料保存及匹配新因子 ID 的最终验证。未知状态保留 pending，不能按完成继续后续流程。

## 即使修复后仍要处理的中断边界

1. **移除和启用是多个请求。** disable 成功、enroll 尚未完成时断网或退出，仍可能暂时没有有效 TOTP；activate 实际成功但响应丢失时，本地可能只能记录未知。不能把超时等同于请求没有执行。
2. **只读复核有有限预算。** `totp_reset_verify.go:10–49` 最多查询 4 次，间隔 0.5、1、2 秒，另加请求及网络重试耗时。持续不同步、401/403 或取消会停止。没有证据证明远端一定在此预算内同步。
3. **验证码与会话都有时效。** 本机时间偏差、验证码跨越有效窗口或会话中途过期可能使激活失败；扩大统一超时不能消除这些问题。
4. **恢复标记不是远端事实。** `old_factor_invalidated=true` 会在发送前作为隔离标志写入；“待恢复”不能单独证明远端旧因子已移除，也不能单独证明新因子未启用。需结合 ACK、实时状态及新因子 ID 判断。
5. **恢复协议尚未形成控制台闭环。** 当前方法要求调用方已认证并持有账号独占权；需要把历史 journal、恢复会话、只读核对和本地提交串起来，才能提供可用的受控恢复入口。

## 已有且应保留的保护

- 移除前先持久化意图、同邮箱隔离标志并读回校验安全凭据。
- 普通重置在移除后确认停用，在激活后核对本次新因子 ID。
- 状态复核仅重复 GET；已发送的安全写请求结果未知时不自动重放。
- 新密钥完成保存与读回前，不执行可选退出所有设备。
- 重启不会自动重新执行未完成的重置；有确切激活及验证证据时，可补做本地持久化。
- 不确定时保留隔离，限制重新登录、再次重置、自动修复及资料导出，防止继续使用可能失效的旧密钥。

这些保护减少后续误操作，但不等于账号能自动恢复。

- `TestLocalAuditIdentityFallsBackAfterHTTPRefusal`：会话 401/403/500 后仍回退 token 账号。

上述审查用例以“复现当前缺口”为断言，因此 PASS 表示缺口已复现，不能称为修复验收通过。现有回归通过也不覆盖这些新增安全要求。

建议修复顺序：禁止无持久存储的首次设置及严格身份确认 → 专用恢复会话及完整登记 journal → 首次设置与重置统一确认规则 → 受控只读核对及恢复入口。不能用清除隔离、直接重跑或无条件加长超时替代这些改进。
